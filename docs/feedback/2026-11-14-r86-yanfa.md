# R86 研发报告 —— 备份快照的隐形修复说破 + sweep 重钉（R85 复验小账清偿）

日期：2026-11-14。基线 v0.5.27。每条标「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、背景（R85 复验期间捡到的题）

R85 远端红框实拍时，坏库服务器（freelist 损坏）在启动 10 秒后打出了 auto 备份包；
开包实测：**包里 quick_check=ok、users=1（数据完好），活库却依旧报错**。原因：备份快照走
VACUUM INTO（桌面与服务器同款），对 freelist/结构级损坏是一次**隐形重建**——包是修好的库，
活库还坏着；数据级损坏 VACUUM 失败 → 降级直拷 → R73 的包自检拦下（备份失败、坏包不落盘）。
两层安全网一直都在，用户不知道「立即备份」在这种坏法下等于修复路——本轮把它说破并锁死。

## 二、做了什么

1. **problems 指引条**（已做并验过）：core `dataHealthCheck` 在 quick_check 不过 + 12 表
   全读得动时，problems 多一条「好消息：点「立即备份」打出来的包是重建过的干净库——把它
   恢复到新程序里，库就修好了。活库本身还坏着：请先不要录单，备份完成后立即联系技术支持。」
   表读不动的深度损坏不给这句（快照多半也打不出来/会被自检拒）。ok 语义不变
   （= problems.length === 0，指引条只在已坏分支追加，探针同源性质保持）。
2. **行为锁 A**（已做并验过）：e2e R86 段，隔离 backupCore 实例（VACUUM INTO 快照钩子与
   桌面/服务器同款）实跑：坏库 → createBackup 成功 → 开包 → quick_check ok + orders 行数
   还在——「坏库打出来的包是重建的干净库」锁死，未来谁换掉 VACUUM INTO 这条会当场红。
3. **行为锁 C + 降级人话**（已做并验过）：隔离实例 snapshotDb 钩子模拟 VACUUM 失败降级
   直拷 → createBackup 拒收 + markFail 原因带「（本次快照降级为直接拷贝：<原因>）」——
   原来只说「备份里的数据库自检没通过，这份包不能用」，看不出被拒的是活库的坏还是包的坏；
   core/backup.ts 失败分支补这层，lastBackupError 里技术支持能分流。
4. **sweep 基线重钉**（已做并验过，R85 复验小账）：/orders 1488.883/506.883 → **1480.117/
   498.117**、/samples 1339.156/357.156 → **1339.359/357.359**——同日两跑一致（R85 复验
   + R86 全链），渲染层零代码改动（R85 复验 diff=0 背书），环境微漂照 R63 先例重钉；
   `/` 路由的提醒条文案是**日期驱动**的（seed 单 2026-11-15 出货，临近必变），不再钉宽度
   与 clipped 文本，只锁 phantom/docOverflow/mainOverflow=0 与两条 reminder-sub 结构。
