## 二、系统性问题（跨页面）

### S1. 统计卡上色规则三页三样：同一个"已收的钱"在详情是绿的、在报表是黑的

- **现象**
  - `.stat-value` 有 4 个颜色变体：`styles.css:503-514`（`.stat.accent` / `.green` / `.amber` / `.red`），默认继承 `--text`。
  - 订单详情 4 张卡（`r4-order-detail.png`）：**订单金额 = 蓝**（accent）、**已收/待收 = 绿**、毛利 = 黑、装箱单 = 黑。
  - 报表 4 张卡（`r4-reports.png`）：**累计销售额 = 蓝**、累计毛利 = 黑、**累计收款 = 黑**、毛利率 = 黑。
  - 工作台 4 张卡（代码 `Dashboard.tsx:60-88`，图过期 🖥）：在途订单 = 默认黑、**待收款金额 = 橙**（amber）、待出货订单 = 蓝（accent）、本月销售额 = 默认黑。
- **量化依据**
  - 「已收到的钱」这一个语义，在 3 个页面用了 **3 种颜色**：详情=绿 `#0f6b4c`、报表=黑 `#1c2333`、工作台"本月收款"=黑。
  - 「待收」用了 **2 种**：工作台=橙 `#8a5200`、详情卡副行=黑（"待收 USD 4,805.00 · 定金 USD 2,341.50"）。
  - 同类元素（`.stat`）在 3 个页面上呈现 3 套规则；而 `styles.css:501` 的注释自己写着"同一屏最多 2 张卡上色"—— 注释守住了**屏内**上限，却没守住**跨页**一致性。
- **为什么是问题**：业务员一天在工作台→报表→订单详情之间来回切。同一个数换了颜色，第一反应是"是不是两套口径"，然后要停下来核对半天。颜色在这里承担的是"这个数要紧吗"的语义，跨页一变，语义就废了。
- **改法**（**只改 class，不动取数、不动金额**）
  1. **定一条规则写进规范**：统计卡**默认全部用 `--text` 纯黑**；只有"需要你今天就动手"的**一个**卡可以用强调色，且全站强调色统一为 `--accent` 蓝（不再是橙/绿/红各来一套）。
  2. `styles.css:503-514`：**删掉 `.stat.green` 和 `.stat.red` 两个变体**（保留会有人继续用），保留 `.stat.accent`；`.stat.amber` 改成只在工作台待收款用（或直接并入 accent）。
  3. `OrderDetail.tsx` 4 张卡：**全部去掉颜色修饰 class**（订单金额、已收/待收、毛利、装箱单）→ 4 张都是黑字。
  4. `Reports.tsx` 4 张卡：**全部去掉颜色修饰 class** → 4 张都是黑字（报表是"读数"的页面，不需要强调色）。
  5. `Dashboard.tsx`：卡 2「待收款金额」保留强调色（它是唯一"待办"），卡 3「待出货订单」**去掉 accent**（订单数不是钱，不需要强调）。
  6. 结果：工作台 1 张蓝卡，详情/报表全黑。跨页稳定，且一屏最多 1 个强调色。
  7. 验收：`r4-*` 三页截图里，除工作台卡 2 外，**统计卡数值区不应再出现绿/橙/红**。

### S2. 一套颜色同时表示"钱"和"货"：绿色一屏出现 4 次，蓝色 3 次

- **现象**
  - `src/renderer/src/ui.tsx:398-416` 两张映射表：
    ```ts
    const PAY_TAG = { draft:'grey', sent:'amber', confirmed:'blue', partial:'amber',
                      paid:'green', settled:'green', expired:'red', void:'grey' }
    const SHIP_TAG = { not_prepared:'grey', preparing:'amber', packed:'blue',
                       shipped:'blue', cleared:'green', delivered:'green' }
    ```
  - 收款状态和出货状态**共用同一套 6 个颜色 class**。
- **量化依据**
  - `green` 被 **4 个状态**共用（payment.paid / payment.settled / ship.cleared / ship.delivered）；`blue` 被 **3 个**共用（payment.confirmed / ship.packed / ship.shipped）；`amber` 被 **2 个**共用（payment.sent / payment.partial / ship.preparing —— 实际 3 个）。
  - `r4-orders.png` 一屏 5 行 × 2 个状态列 = 10 个 tag，出现 **4 种底色**（灰/黄/蓝/绿）：待确认(黄)、客户已确认(蓝)、已结清(绿)、已收款(绿)、未备货(灰)、已签收(绿)、备货中(黄)、草稿(灰)、已作废(灰)。
  - `r4-dashboard.png` 一屏 6 行 2 列 = 12 个 tag，同样 4 种底色。
  - 订单列表里「收款状态」和「出货状态」**紧挨着两列**，同一个绿色 tag 既出现在左列（已收款 = 钱）又出现在右列（已签收 = 货），中间只隔 100px。
- **为什么是问题**：
  - 蓝/绿在低质量笔记本屏和色弱下几乎分不出来，而"已收款"和"已签收"对业务员是两个完全不同的任务。
  - 更糟的是**颜色失去了信息量**：同一屏里 4 个绿 tag 表达 4 件事，那"绿"就不再等于"这单好了"，等于"这单是某件好事"。颜色只有在全局一对一的时候才有用。
- **改法**（**推荐方案 B，成本最低、收益最大**）
  - **方案 B（推荐）**：**只有"收款"维度上色，"出货"维度一律中性**。
    - `ui.tsx:409-416` 的 `SHIP_TAG` 六个值**全部改成 `'grey'`**（保留 `PAY_TAG` 不动）。
    - 出货进度靠**文字**区分（未备货 / 备货中 / 已装箱 / 已发出 / 已清关 / 已签收）—— `.tag.grey` 是中性底灰 + `--neutral-text`，不参与红黄蓝绿的语义竞争。
    - 代价：出货状态"做完了"没有绿色提示。**如果业务不接受**，用方案 A。
  - **方案 A**：给出货维度单独一套 class，**不与收款共用色相**：
    ```css
    /* styles.css，紧跟 .tag 段（710-740）之后 */
    .tag.ship-grey   { background: var(--surface-3); color: var(--text-dim); }
    .tag.ship-amber  { background: var(--warning-soft); color: var(--warning); }
    .tag.ship-blue   { background: var(--accent-soft);  color: var(--accent-hover); }
    .tag.ship-green  { background: var(--success-soft); color: var(--success); }
    ```
    `SHIP_TAG` 改成 `not_prepared:'ship-grey', preparing:'ship-amber', packed:'ship-blue', shipped:'ship-blue', cleared:'ship-green', delivered:'ship-green'`。
    —— 但这样绿还是同时出现在两列，只是"换了个名字"，**治标不治本**，所以我更推荐 B。
  - **验收**：`r4-orders.png` 一屏最多 **3 种底色**（收款那 3 种 + 出货的灰），且**绿色只出现在收款列**。

### S3. PI 号是全站唯一一个被弱化成灰的编号列

- **现象**（对截图做「最深像素取色」，不是肉眼估）
  - `r4-orders.png`：订单号 `SO20261021005` = **`#1C2333`（`--text` 黑）**；**PI 号 = `#5C6878`（`--text-faint` 灰）**，且被截断成 `PI202610210…`。
  - `r4-quotations.png`：报价号 `Q20261021001` = **`#1C2333` 黑**。
  - `r4-samples.png`：样品单号 `SMP20261021002` = **`#1C2333` 黑**。
  - `r4-products.png`：款号 `PL-002` = `#1C2333` 黑。
  - `r4-customers.png`：公司名 / 联系人 = `#1C2333` 黑；国家 / 邮箱 / 电话 / 地址 = `#667085`（`--text-dim`，**四列一致** ✓）。
- **量化依据**
  - 6 个列表页的标识列里，**只有 1 列用了 `--text-faint`**：`Orders.tsx:137` `<td className="mono nowrap faint clip-100" title={o.piNo}>`。
  - 同一张订单表里，**创建日期**也用 faint（`Orders.tsx:165`）—— 日期弱化合理，PI 号弱化不合理。
  - `--text-faint #5c6878` 在白底上对比度约 **5.9:1**，能读，但**明显比旁边的黑字低一档**；业务员把 PI 号截图发到群里核对时（白底），灰字最先被忽略。
- **为什么是问题**：`--text-faint` 在这个界面里的语义是「次要、可忽略」。**PI 号是这张单的对外唯一标识**（客户手上的单据号就是 PI 号），把它弱化等于系统在说「这个号不重要」。
- **改法**（**只改 className，不动截断逻辑**）
  1. **规则**：列表页的**编号类列一律 `--text` + `.mono`**；可点性由整行 hover 底色（`styles.css:549` `tr.clickable`）承担。`.faint` 在表格里**只允许用于日期等真·次要信息**。
  2. `Orders.tsx:137`：`className="mono nowrap faint clip-100"` → `className="mono nowrap clip-100"`（**去掉 `faint`，其它不动**）。
  3. 客户页那 4 列 `--text-dim` **不要动** —— 那是**一致**的（国家/邮箱/电话/地址四列同色同档），R2 我说过「只有一列灰」的问题现在不存在了。
  4. 验收：`r4-orders.png` 里，PI 号与订单号取色应同为 `#1C2333`；创建日期保持 `#5C6878`。

### S4. 同一个弹窗里 label 一半双语一半中文；双语是给单据用的，不是给表单用的

- **现象**（`r4-modal-product.png` = 新增商品弹窗）
  - 双语 3 个：`款号 Style No. *` / `品名 Description` / `成分 Composition`
  - 纯中文 10 个：`单件净重（kg，可空）` / `每箱件数（可空）` / `箱规（长×宽×高 cm，可空）` / `成本价（工厂价，可空）` / `类目` / `品牌 / 季节` / `尺码表（本款号自有，可任意填写）` / `颜色表（本款号自有）` / `备注` / `商品图片（PI 会显示主图）`
  - 订单弹窗（`Orders.tsx:369-546`）：客户 / 币种 / 汇率 / 贸易术语 / 装运港 / 目的港 / 付款方式 / 定金比例 / 预计出货日 / 预计到港日 / 客户 PO 号 / 备注 —— **14 个全中文，0 个双语**。
- **量化依据**
  - 商品弹窗 12 个 label：**3 双语 / 9 纯中文**（25% 双语）。
  - 订单弹窗 14 个 label：**0 双语**。
  - 打印单据（PI/PL/CI）双语 **是必须的**（发给海外客户），而应用内弹窗是业务员自己用的。
- **为什么是问题**：`款号 Style No. *` 比 `类目` 宽近一倍，同一个 3 列栅格里 label 左右不齐；更本质的是，用户看到一半英文一半中文会以为**这是两套表单**（"哦，英文那三个是必填的？"）。
- **改法**（**方案 A，推荐**）
  - `Products.tsx:269` `款号 Style No. *` → `款号 *`
  - `Products.tsx:277` `品名 Description` → `品名`
  - `Products.tsx:287` `成分 Composition` → `成分`
  - 规范补一条：**应用内表单 label 一律中文**；中英双语只出现在 PI / PL / CI / 报价单这 4 种要发出去的打印件上。
  - 成本 3 行，收益是全站表单栅格第一次能对齐。
  - （另一个选项是全站双语 —— 12 个页面 100+ 个 label，不划算，不做。）

### S5. 状态列形态不统一：同一页里既有下拉框又有色块，而且看不出哪个能点

- **现象**
  - `r4-samples.png` 打样单：「状态」列 = **`<select class="sm">` 下拉框**（可编辑），「打样费收款」列 = **只读 tag**（未收=琥珀 / 下单抵扣=蓝）。
  - `r4-quotations.png` 报价：「状态」列 = **下拉框**，「结果」列 = **只读 tag**（待回=琥珀）。
  - `r4-orders.png` 订单：两个状态列**都是只读 tag**。
- **量化依据**
  - 3 个列表页共 4 个状态列：**2 个下拉、2 个只读 tag**，且**没有任何一个页面是"全下拉"或"全 tag"**。
  - 下拉框尺寸：报价「状态」约 92×22px；打样单「状态」约 80×22px；原生箭头几乎贴着文字（"草稿▾"、"已寄出▾"）。
  - 只读 tag 一律 20px 高、pill 圆角、内边距 `0 8px`（`styles.css:710-719`）—— **比下拉框矮 2px**，两种控件在同一行里高度不齐。
- **为什么是问题**：只读 tag 和可编辑下拉长得不像，用户**看不出哪个能点**，会去试着点那个灰 tag（点了没反应 = "坏了"）。而且每换一页要重新学一次控件形态。
- **注意**：规范 `docs/ui/design-system.md` §5.6 早就写明了「**列表一律 tag（只读），可编辑状态一律在详情页/编辑弹窗里用 select**」—— R1 写进规范、R2 又提过一次、R3 只改了报价的「结果」列。**这是第三次没落实**，本轮要做掉。
- **改法**
  - **原则写进规范**：**列表页的状态列一律只读 tag**；改状态去详情页（订单详情右侧「状态推进」区有「改状态」按钮，打样单/报价详情同理）。
  - `Samples.tsx` 状态列的 `<select className="sm">` → 只读 `.tag`（颜色按 status 映射，**不复用 `PAY_TAG/SHIP_TAG`**，打样状态自己一套 4 个 class：`grey/amber/blue/green`）。
  - `Quotations.tsx:171` 状态列的 `<select className="sm">` → 只读 `.tag`（报价状态自己一套）。
  - **注意**：这是**去掉一个编辑入口**，属业务取舍 → **要周文娟点头**。如果周文娟坚持列表里直接改状态，则**必须**给可编辑的下拉加一个统一的"行内编辑"标记（例如 select 左侧加一个 12px 的 ⌄ 铅笔图标，或改成 ghost 按钮 + 菜单），**不能和只读 tag 混排**。
  - 无论走哪条，`.select.sm` 的 `min-width` 从 64px 提到 **80px**，箭头别贴字（R3 报告自己列了这条"没做"）。

### S6. 长文本两种截断法：列表用省略号（对），输入框直接切尾巴（错）

## 附：设计规范增补（R3，已同步到 `docs/ui/design-system.md`）

1. **统计卡**：默认 `--text`；一屏最多 **1** 张强调色卡，强调色只用 `--accent`；不新增颜色变体（删 `.stat.green` / `.stat.red`）。
2. **状态色按维度分家**：收款维度 = `PAY_TAG`（灰/琥珀/蓝/绿/红）；出货维度 = `SHIP_TAG`（一律中性灰）。**一个颜色不得跨维度复用。**
3. **编号列**：`.mono` + `--text`，截断时用 `.cell-clip` / `.clip-100` + `title`；`.faint` 不用于编号列。
4. **表单 label 一律中文**；中英双语只允许出现在 PI / PL / CI / 报价单这 4 种外发单据上。
5. **表格状态列一律只读 tag**（20px 高 / pill 圆角）；可编辑控件不进列表页状态列。
6. **统计卡副行**多值时用 flex + `gap: var(--space-3)`，不要用中点挤。
