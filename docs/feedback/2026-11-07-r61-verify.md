## 四、本轮新发现（第一条不是小账，下轮要还）

1. **备份接口的 EACCES 还是「服务器内部错误」——他这轮修的人话，被他这轮新加的路漏掉了**。复现：chmod 000 服务器的备份目录 → 点「立即备份」（或 curl `/api/backup/create`）→ toast 是干巴巴五个字「服务器内部错误」。根子在 `core/backup.ts:143`：打包失败时 `throw new Error(msg)` 把原始错误重新包了一遍，`.code` 没了，`AllExceptionsFilter` 的 `isFsError`（认的就是 `.code`）认不出，落进「未处理的错误」。docs 那条他修好了（我亲测人话），说明过滤器和映射本身没毛病，就是备份这条路把错误包瞎了。**不算致命**：备份失败本身大声失败了（设置页黄条会挂「上一次备份没成功」，只是挂的是英文原文 `EACCES: permission denied, open '…'`，我也看不懂），数据一分没丢。但备份是钱的凭据，这话术正是 R60 我点名的那句，不能在新路上又裸奔一次。修法一句话：把原始错误原样往外抛（或者把 code 挂回去），别 `new Error(msg)`。
2. **恢复之后「最近一次成功备份」跟着旧库走**。整库恢复连 `backup_state` 一起换成了备份那一刻的内容——我在远端恢复完，「服务器最近一次成功备份」显示的是备份包里的旧时间。原理上没毛病（恢复=回到那天），但设置页那句会短暂说谎，下一次备份才自愈。记账即可，不值得为此单独立柱子。
3. **服务器备份列表的体积全是「0.0 MB」**。包才 12KB，`(size/MB).toFixed(1)` 一除就是 0.0。看着像坏了似的，改成 KB 起步或者小于 0.1MB 显示实际字节数都行。纯显示，随手修。
