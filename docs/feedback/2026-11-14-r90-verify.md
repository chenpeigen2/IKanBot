## 四、缺表副本挂死教训——读核判断（未真复现挂死）

按任务口径不真复现 rc=124（费时且卡会话），用代码读核判断叙事是否自洽，判断方式如实记录：

1. **migrate 入口**（electron/db/index.ts:213–235）：对 user_version 落后的库逐条
   `BEGIN → database.exec(m.sql) → PRAGMA user_version → COMMIT`，失败 ROLLBACK 并抛
   「迁移失败 (vN …)」。MIGRATIONS 的 SQL 是**裸 CREATE TABLE**（schema.ts 全篇 26 张表，
   非 CREATE TABLE IF NOT EXISTS——任务口径里写的是 IF NOT EXISTS，措辞小出入，不影响
   论点）——建表要分配/写页，撞上坏 freelist 就会失败甚至卡死。
2. **主进程兜底**（electron/main/index.ts:231–240）：openDb 抛错 → `dialog.showErrorBox`
   （**同步 API，要等人点确定**）→ `app.exit(1)`。自动化环境没人点确定，进程停在弹窗上，
   shot.sh 的 60 秒 timeout 强杀 → **rc=124**。研发观察到的「挂死」与这条代码路径自洽
   （无论卡在 sqlite exec 还是卡在 showErrorBox，自动化口径都表现为超时）。
3. **「真机缺表本来会被 migrate 修回来」**这句只对 user_version 落后的副本成立（migrate
   循环会重建）；user_version 已是最新但表被删的副本 migrate 会跳过、不修——不过那种副本
   能开机，stats 报错进早退分支、health 报「核心表读不出来」→ 红条照样拦（另一条已覆盖的
   路）。README 教训的实操指向（别拿缺表副本开真机；深损坏实拍配方用「页内容坏」不用
   「缺表」）是对的。

结论：叙事自洽，判据为上述三处代码读核 + 我对「migrate 能过 / stats 炸」边界的副本实测
（user_version 25 = LATEST 时 migrate 空跑、COUNT 索引扫描可活、表页读必炸），未真复现挂死。

## 九、挑刺（均非打回项）

1. **r90 README 教训的措辞精度**：「真机这类『缺表』本来会被 migrate 修回来」只在

   红条覆盖的另一条路）。实操指向没错，但那句话作为一般结论偏宽——记一笔，不用改。

   CREATE TABLE IF NOT EXISTS——「要写页」的论点不受影响，纯记录。
3. **e2e R90 锁的强度**：`match(/healthBanner/g).length >= 3` 是下限锁——将来若有人把
   healthBanner 复制成四份散着用（不共用同一个组件）也过锁。当前实拍与结构读核兜底，
   风险低，与仓库 renderer 无 DOM 工装的现状一致，可接受。
4. **sweep 基线本轮未复跑**：研发报「sweep 与重钉基线一致（常态值）」，我的任务口径
   （build/test:all/typecheck/两红验证/实拍）不含 sweep；e2e 内 R89/R90 锁已绿、本轮改动
   不碰 sweep 覆盖的提醒/备份口径，风险低——如实记「没验」。
