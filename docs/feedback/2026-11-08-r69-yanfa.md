# R69 研发报告 —— 恢复对账的语义小账（R68 复验挂账）

日期：2026-11-08。基线 v0.5.10。每条标注「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **恢复失败不留孤儿标记**（已做并验过）：标记武装/撤除/恢复编排抽成 services 的
   `restoreBackupWithReport(path)`（arm → try restore → catch disarm + rethrow），ipc 本机分支
   改调它。恢复抛错（坏包/已在恢复/路径非法）标记跟着撤——失败不再给下次启动留一个把
   「当前库」算成「恢复后对账」的假账（R68 复验挂账第 2 条）。桌面 e2e 两条真行为断言：
   坏路径恢复被拦且标记被撤、成功恢复标记留给补算。
2. **seed 清恢复对账键**（已做并验过）：`last_restore_report` / `pending_restore_report` 随
   seed 归零（先例 d851ffd：seed 是「重建」，基线要能复现）。e2e 源码 grep 锁。
3. **e2e 段位修正**（已做并验过，首跑实锤）：桌面钩子 `keepRestoringAfterRestore=true`，
   成功恢复后旗子举到进程死——R69 段原先放在套件中间，成功恢复一次就把后面 R36/R43 等段的
   恢复相关断言连环打红（「已经在恢复备份了」×2、「没在恢复时不挡任何通道」×3）。段移到
   套件最末，段内恢复后手动 `openDb()` 模拟真桌面的重启重接。
4. **README 断言规模**（已做并验过）：2500 → 2507。
