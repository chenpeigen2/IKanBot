## 二、系统性问题（跨页面）

### S1. 【头号】打印单据的合计行与表头列数对不上，总数印错列

- **现象**
  - `src/shared/documents.ts:290-296`（PI）和 `:602-608`（报价单）的 tfoot 合计行都是：
    ```html
    <td colspan="6" class="center">TOTAL / 合计</td>
    <td class="num">${fmtQty(totalQty)}</td>   <!-- 数量 -->
    <td></td>
    <td class="num">${order.grandTotal.toFixed(2)}</td>  <!-- 总额 -->
    <td></td>
    ```
    这张表是 **9 列**（Style No. / Photo / Description / Color / Size / Qty / Unit Price / Amount / Sub-total，见 `documents.ts:273-282`）。`colspan=6` 已经吃掉了 Style→Size→**Qty** 六列，于是：
    - 总数量落进第 7 列 = **Unit Price 单价**
    - 总额落进第 9 列 = **Sub-total 小计**（PI 因为列宽重算侥幸落在 Amount，报价单就落在小计列了）
    - 5 个 td 合计占用 10 个列槽 > 表头 9 列 → **tfoot 多出一个表头里不存在的"幽灵第 10 列"**。
- **量化依据**（对 `out/shots/r2-doc-pi.png` / `r2-doc-quotation.png` 做垂直边框像素扫描）
  - PI 表 9 列的列边界（表头行与数据行完全一致）：`45, 116, 179, 333, 389, 438, 495, 558, 635, 713`
    → Qty=438~495、Unit Price=495~558、Amount=558~635、Sub-total=635~713
  - PI 合计行的边框：`45, 495, 558, 635, 713, 747`
    → `900` 落在 **495~558 = Unit Price 单价列**（偏右 57px）；`7805.00` 落在 558~635 = Amount ✓；`713~747` 是**幽灵第 10 列**（表头里根本没有，宽度 34px）。
  - 报价单合计行：`700` 落在 495~558 = **单价列**；`5540.00` 落在 **635~713 = Sub-total 小计列**（应落在 558~635 的金额列，**偏 72px**）。
  - 同一问题在应用内预览弹窗里一样能看到：`out/shots/r2-modal-pi.png`，PI 预览的合计行就在折叠线下面。
  - **CI 单据（`documents.ts:786`，8 列，`colspan="4"`）是对的**，别照着改坏了。
- **为什么是问题**：PI / 报价单是要发给海外客户的正式单据。**总数量印在"单价"列下面，客户一眼就看出来这单做得不专业**；总额印在"小计"列则和上面的分项小计混在一起。这是本轮唯一一个"发出去会丢单"级别的问题。
- **改法**（只改 colspan 和格子数，**一个金额计算都不动**）
  1. `src/shared/documents.ts:290`（PI）与 `:602`（报价单）：把合计行改成
     ```html
     <tr class="total">
       <td colspan="5" class="center">TOTAL / 合计</td>   <!-- Style No.→Size，5 列 -->
       <td class="num">${fmtQty(totalQty)}</td>          <!-- Qty -->
       <td></td>                                        <!-- Unit Price -->
       <td class="num">${order.grandTotal.toFixed(2)}</td><!-- Amount -->
       <td></td>                                        <!-- Sub-total -->
     </tr>
     ```
     即 **`colspan="6"` → `colspan="5"`**，合计正好 5+1+1+1+1 = 9 列。
  2. 验收：重跑 `node_modules/.bin/electron scripts/shoot-doc.cjs out/shots/pi.html out/shots/check-pi.png`，合计行边框应变成 `45, 438, 495, 558, 635, 713`（**没有 747 那个幽灵列**），`900` 落在 438~495（Qty 列），`7805.00` 落在 558~635（Amount 列）。
  3. **CI 不要动**（`documents.ts:786` 已经是 8 列对 8 格）。
  4. 顺带（可选，同一处）：`documents.ts:197/524/705` 的 `<td class="num sub-total">小计 ${x}</td>` 里的"小计"二字和表头 `Sub-total/小计` 重复，**建议单元格只放数字**，让这一列的数和小计列头对得上竖线（可选，不做也不影响本条验收）。
  > 研发 R1 的说法是"单据纸面不动"。我的意见：这是**排版错位**，不是业务口径，金额一个字节都不改，属于 UI 范围。

### S2. 订单表 / 打样单表仍然横向滚动，最后两列永远看不见

- **现象**：`.table-wrap { overflow-x: auto }`（`styles.css:503`），两张表的内容宽超过容器。
- **量化依据**（运行时实测）

  | 页面 | 列数 | `table.scrollWidth` | 容器 `clientWidth` | 溢出 |
  |---|---|---|---|---|
  | 订单 `/orders` | 13 | **1292px** | 1166px | **+126px** |
  | 打样单 `/samples` | 14 | **1402px** | 1166px | **+236px** |
  | 报价 / 商品 / 客户 / 报表 | 7 / 8 / 7 / 7 | 1166 | 1166 | 0 ✓ |

  1366px 笔记本上主区 = 1366−208−48 = 1110px，打样单溢出 **292px**。
  各列实际宽度（订单）：订单号 117 / PI号 117 / 客户 144 / 货值 100 / 含费用合计 100 / 件数 48 / 已收 100 / 待收 100 / 收货状态 100 / 出货状态 76 / 预计出货 90 / 创建日期 90 / **操作列 100**。
  各列实际宽度（打样单）：样品单号 116 / 客户 136 / 日期 82 / **款号 116** / 件数 40 / 样品费 52 / 快递费 54 / 公司净垫 64 / 待收 64 / 状态 84 / 打样费收款 80 / 快递单号 102 / 寄出/签收 104 / **操作列 196**。
- **为什么是问题**：打样单表最右的「寄出/签收」和「操作」两列（合计 300px）在 1366px 屏上**永远看不到**，必须横向拖 292px。业务员每天扫几百行，"扫到右边再回来"是最费眼睛的姿势。
- **改法**（**不需要业务拍板，纯 CSS + 复用已有组件**）—— 我已经用注入 CSS 实测过：
  1. `styles.css`：
     ```css
     .content { padding: var(--space-5) var(--space-4) var(--space-8); }  /* 24px → 16px */
     table.data th, table.data td { padding: var(--space-2); }              /* 12px → 8px */
     ```
     实测效果（`out/shots/r2-probe-fix-orders.png` / `r2-probe-fix-samples.png`）：
     **订单表 1292 → 1188px，容器 1166 → 1182px，溢出从 126px 降到 6px**；
     **打样单表 1402 → 1290px，溢出从 236px 降到 108px**。
  2. 订单表再省 6px：`.content` 横向 padding 用 `var(--space-3)`(12px) 而不是 16px，或把「PI号」列加 `.cell-clip` + `max-width:100px` + `title`。**订单表横向滚动条即可消失。**
  3. 打样单表还差 108px —— **用「操作列收进 ⋯ 菜单」补掉**（见 S3）：打样单操作列 4 个文字链占 **196px**，换成「转订单」文字链 + 一个 `⋯` 菜单后 ≈ **56px**，**省 140px**；再把「款号」列 `.cell-clip` 到 96px（省 20px）、「快递单号」列 clip 到 100px（省 2px）。合计 1290 − 140 − 20 − 2 = **1128px ≤ 1182px → 滚动条消失**。
  4. **验收**：重截 `/orders` 和 `/samples`，底部不应再出现横向滚动条；`r2-probe-*.png` 的 `overflow` 字段应为 0 或负数。

- **现象**：所有列表页最后一列是几个 `<a>`/`<span onClick>` 文字链，**中间既没有空格、也没有竖线、也没有按钮底**。

### S6. 报表页拿"黄色警告条"装操作说明，而且报表里"没有值"有三种写法

- **现象**
  1. `Reports.tsx` 页面上方一条 `.alert.warn`（琥珀底 `#fdf2dd` / 字 `#8a5200`），内容是"有成本记录不全的单：2026-10（1 单）…补录入口：到「订单」里打开那一单 →「商品明细」表 → 成本那一栏直接填数字"。**这是操作指引，不是警告**。R1 已点名（P7），排到 R2，本轮**仍未做**。
  2. 同一张「月度汇总」表里，"没有毛利"有两种写法：2026-10 行显示 `—`（毛利、毛利率两列），2026-03 / 2026-02 行显示 `CNY 0.00` 和 `0.0%`。
  3. 报表页 4 张统计卡里，「累计毛利」的值是一个绿色的 `—`（`--success` 色），「毛利率」是黑色的 `—` —— **同一个"没有数据"用了两种颜色**。
- **量化依据**：`.alert.warn` 底色 `#fdf2dd`（R1 记录对比度 3.82:1，R1 改色后字色已加深到 `#8a5200`，约 5.76:1，**这一条 R1 修好了**）；但**语义错位没修**。表内空值写法实测：3 行 × 7 列中，出现 `—` 2 次、`CNY 0.00` 2 次、`0.0%` 2 次，共 **3 种"空"的长相**。
- **为什么是问题**：黄色警示条在 B 端里等价于"出错了"，业务员每次进报表页都被吓一下，然后发现其实没事。空值三种写法则让"这一行到底是 0 还是没数据"变成每次都要重读一遍的事。
- **改法**
  1. `Reports.tsx`：`.alert.warn` → `.alert.info`（`styles.css:707` 已有 `.alert.info`，底 `--accent-soft` / 字 `--accent-hover`，对比度 5.60:1）。如果确实要强调"有 1 单成本不全"，**把这 1 单做成一个可点的行/链接**，而不是塞在说明条里。
  2. 统一空值写法：报表页的"缺数据"一律用 `—`（`--text-faint`），**不要用 `CNY 0.00` 表示"没数据"**；真正算出来是 0 才写 `CNY 0.00`。这一条属于**呈现口径**，若周文娟认为"0 和没数据就该一样"，就反过来把 `—` 全换成 `CNY 0.00`，**二选一，全表统一**。

### S7. 设置页所有输入框都拉满，短字段也拉满

  - 「收款账户」里「银行地址」input 宽 1130px，「账号」宽 568px

### S8. 侧边栏 8 个 Unicode 字符当图标，字形重量严重不均

- **现象**：`App.tsx:15-22` 侧栏 8 个导航项的图标是 `◧ ✎ ▤ ✂ ▣ ☰ ▦ ⚙`（纯 Unicode 字符，非 SVG）。
- **量化依据**（运行时读取 `.nav-icon` 文本与盒模型）：8 个图标盒高**都是 20px**，但：
  - `◧`（工作台）、`▣`（商品库）、`▦`（报表）是**实心块**，视觉重量最大；
  - `✎`（报价）、`✂`（打样单）是**细线笔画**，视觉重量最小；
  - `☰`（客户）用的是"三横线"这个**列表**符号，但客户页是个列表页，语义还算对；`⚙`（设置）是齿轮。
  - 这些字符来自**不同的 fallback 字体**（Segoe UI Symbol / MS Gothic / DejaVu），实测盒高虽然都是 20px，但**基线位置和实际墨迹高度不同**（`▤` 的墨迹只到盒高的 70%，`⚙` 满格），在深色底上"▤"看起来明显比"⚙"小一圈。
- **为什么是问题**：侧栏是**每天点几十次**的地方。8 个图标有 3 种重量，扫视时"商品库"的实心方块比"报价"的细铅笔重得多，**会先被扫到**。另外 `✂`（剪刀）表示"打样单"、`▣`（方块）表示"商品库"，是设计师随手挑的，**没有任何统一规则**。
- **改法**
  1. **首选（推荐）**：换成一套统一的 16×16 线性 SVG 图标，`stroke-width: 1.5`、`stroke: currentColor`、视窗统一 16×16，8 个图标同一个文件里定义（建议新建 `src/renderer/src/components/NavIcons.tsx`）。颜色直接用 `currentColor`，`.nav-item.active` 自动变白。
  2. **本轮若不换 SVG 的降级方案**（零依赖、1 行 CSS，但会改变用户习惯，**需周文娟点头**）：
     ```css
     .nav-icon { display: none; }
     .nav-item { padding-left: var(--space-4); }
     ```
     侧栏只有 8 项，文字全够认；去掉图标后侧栏会安静很多。
  3. **无论走哪条**，`.nav-icon` 都要改成固定 16×16 的盒（`width:16px; height:16px; display:inline-flex; align-items:center; justify-content:center;`），**不要让图标参与文字基线对齐**。

## 三、单页问题

### P1. 工作台 `/`：待办圆点还是"靠颜色认"，红/黄/蓝分三档

- **为什么是问题**：7px 的圆点在小尺寸笔记本屏上、或者低亮度屏上，**红和橙几乎分不出来**（`#a53024` vs `#8a5200` 在缩放后的暗背景上）。业务员看到"红点"不知道是"该收钱"还是"该确认"。

### P2. 工作台"最近订单"表：`USD 0.00` 和真的 0 长得一样
