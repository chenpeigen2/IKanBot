## 二、逐项亲验记录

### ① 真窟窿实锤——R66 的 inspect 真的没做版本检查（我先认账）

拿两版源码对照：

- **R66 版（0d9d44b）**：quick_check + user_version 检查**只在 `inspectRestoredDb`（恢复路）里**
  （旧文件 335-339 行）；`inspectBackup`（上传/摘要的闸门，旧文件 464-500 行）里
  `grep user_version` **零命中**——搬上来的「未来包」只要有核心表就能过摘要、拖到恢复才拦。
  且 R66 版注释还写着「inspect 闸门（zip 结构、quick_check、版本守卫）」——注释吹了没做到的牛。
- **HEAD 版（f98fc4e）**：抽出 `assertDbProbeUsable`（331 行，quick_check + user_version 人话守卫），
  **定义只有一处**，调用两处：`inspectBackup:497` 与 `inspectRestoredDb:354`（restoreBackup:600 调它）
  ——两条路同一道闸。

**这里我先认账**：我 R66 复验时验了 importBackupZip→inspectBackup 的调用链、也看到了文件里的
user_version 检查，但没核对那个检查块**在哪个函数里**——「同一道版本守卫」的结论下早了。
研发这轮是给上传版本守卫写专属断言时实锤的（红态死在「这个备份包打不开来看：no such table:
orders」，修后才是「请先把程序升级到该版本或更高」），真窟窿、真修法，这个找茬我服。

### ② 「话术逐字一致」——验到了比逐字更强的形态

话术字符串现在**只有一份定义**（`assertDbProbeUsable` 内）：
`这份备份来自更新的程序版本（数据格式 v${v}，当前只认到 v${LATEST_DB_VERSION}）。请先把程序升级到该版本或更高，再恢复。`
inspect 与 restore 两个调用点引用同一份——想让它俩不一致都难。这就是「同一道闸」的最强形态，
不是两处粘贴同一段话（那种会被将来某次单点修改糊弄掉）。

### ③ 断言实况——两条都真

- **HTTP「来自未来的包被人话拦（先升级程序再打开）」**（`server/test/e2e.ts` 搬迁上传节）：
  真造了一份 v999 包（裸驱动钉 user_version=999，避开 server 自动迁移把版本拉回去——这个细节
  处理得对），真 POST /api/backup/upload → 400 + 消息含「升级」。
  修前这条会死在「打不开来看：no such table: orders」（红验证记录与缺口形状吻合）。
- **双模式「同一包的摘要+恢复只上传一次，且服务器自己的包不被误传」**（`scripts/mode-test.ts`）：
  摘要 + 恢复两次调用后，数服务器备份目录里 `-imported` 文件**恰好 1 份**——没有缓存的话两次调用
  会落两份，这条计数是真牙。

### ④ 判据修正——「服务器先认领」真改了，existsSync 误传的口子真堵了

`electron/ipc/index.ts` `resolveRemoteBackupPath` 现在是三段式：先 `remoteCall('backup:inspect', [path])`
让服务器认领（认领成功 = 服务器自己的包，原样用）；认领失败且本机确有此文件 → `remoteUploadBackup`
（会话内缓存）；两边都没有 → 人话「这份备份包服务器上没有，本机也没找到」。同机部署下
existsSync 会把服务器自己的包误传一份的口子（R66 版判据）真堵上了——双模式那条计数断言
（imported 恰好一份）就是它的回归锁。

### ⑤ 场景闭环（可选项做了）——老程序收 v25 包，两条路同一句人话

代码层面已闭环（字符串一份定义、两处调用）；测试层面两条路各有绿断言：上传路是本轮新增的
v999 包 400+「升级」（HTTP 220 那条），恢复路是桌面 e2e 既有的三条「数据格式比当前程序新的包拒 /
报错说清了当前只认到 v几 / 给了出路（先升级程序再恢复）」——本轮日志 1060-1062 行全绿。
v25 包在 v0.5.4 老程序上不管从列表恢复还是从上传进来，都会被同一句「请先把程序升级到该版本或更高」
拦下——与我最初那个 v25 弹窗同源同话术，闭环成立。

## 三、新发现 / 疑点

1. **纯远端部署下，服务器侧「未来包」的话术会被换成不准的一句**（本轮判据修正的边角）：
   `resolveRemoteBackupPath` 的探针 inspect 失败时**吞掉原错误**，若本机也没有同名文件，抛的是
   「这份备份包服务器上没有，本机也没找到」——但那个包明明在服务器上，只是版本超前。闸门仍拦得住
   （恢复不了），只是人话误导：远端用户对列表里的未来包点「看摘要」会以为包丢了。同机部署（本轮
   修的主场景）反而没事：探针失败 → 本机同名文件存在 → 上传 → 服务器重验 → 弹的是正确的版本人话。
   建议：探针失败时区分「服务器没这个路径」与「inspect 业务错误」，后者原样往外抛。不拦本轮。
2. **「且不留在备份列表里」名大于断言**（HTTP 未来包那条）：check 体只验 400 + 含「升级」，
   「不留列表」靠的是 `importBackupZip` 里验不过当场删的代码（我读了，真有），但没有列表核对断言。
   与 R64/R66 的计数口径同家族——代码在、断言没锁，记一笔。
3. **「不含 manual」子句在现命名下是空转**：服务端 upload 忽略 `?name=` 参数（控制器只读 body），
   所有上传一律命名 `ikanbot-<时间戳>-imported.zip`——所以 `importedFiles.filter(f => f.includes('-manual'))`
   恒为 0，「服务器自己的包不被误传」实际靠 `importedFiles.length === 1` 这个计数撑着（这就够了，
   误传必多一份 imported）。顺带：客户端发的 `?name=` 是个死参数。都不影响行为，记一笔。
4. **我的 R66 复验报告追加了追记后，VERDICT 行不再是文件末行**——追记内容属实、交代清楚，
   但复验报告的 VERDICT 行按纪律应是末行（后续按文件尾取判词的工具会读错）。小事，提个醒。
