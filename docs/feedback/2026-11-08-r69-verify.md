## 三、新发现 / 疑点

1. **「seed 清 pending_restore_report」的下半句是空防**：全仓库**没有任何代码写** `pending_restore_report`
   这个 settings 键——真正的补算标记是 userData 根目录的**文件** `restore-report-pending`（seed 只碰
   db，碰不着文件，语义上也碰不着：标记在说明恢复真发生过，seed 不该吞它）。所以 seed 里第二条
   DELETE 是防「将来有人真用这个键」的空防，报告「seed 清 last_restore_report / pending_restore_report」
   的表述会把读者带偏（以为标记文件也被清了）。顺带：`services/backup.ts:105` 的注释还把标记文件
   叫成「pending_restore_report 标记」（旧名残留）。两处都是表述账，行为无害，记一笔改注释即可。
2. **「六条」实为 7 条**：与前两轮同家族的计数口径（把「被拦+被撤」并成一组数）。+7 增量精确，
   不算虚报，提个醒。
3. 边角里的边角（只记不追）：恢复 → seed → 重启（中间不启动）的序列里，pending 文件还活着，
   settle 会对 seed 后的库补算一份对账——语义上「恢复确实发生过」所以不算错账，但那张卡的内容
   与 seed 后的库对不上历史。sweep 用临时目录够不着这个序列，真实使用也极难踩到，知道有这回事就行。
