## 三、四条新锁抽验两条（拆到合同层 + 实弹）

### (a) orders/delete——空单整单删除锁：**守卫段与剧情对得上，实弹复测通过**

- **守卫段**（core/orders.ts L1360-1431）：`blockersOf` 七项计数——明细/收款/核销/装箱/
  存档/照片/由它转出的打样单——任一非零即拒；另有作废单拒删、未撤销预收抵扣拒删；
  且「还是空单」的确认与 DELETE 在**同一条语句**里做（8 个 NOT EXISTS），防查删之间
  落新凭据的竞态；删除未生效时按最新状态说人话。复核单给的守卫描述（明细/收款/核销/
  装箱/存档/照片/转单任一非零即拒）逐项对上。
- **e2e 剧情**：新建无明细单 → `delete` 200 → `get` 200 且 `text === ''`（get 对已删单
  回 null，Nest 对 nil body 发空体）——与守卫的空单放行分支对应。
- **实弹**：我用与 e2e 同款启动路径（Nest Test module + configureApp + 临时 SQLite，
  独立组一遍，/tmp 一次性脚本用完即删）复测：delete 200 空体、get(已删单) 200
  text=`''`——通过。
- 「非空单拒删」半边：HTTP 面没锁，但桌面 e2e（scripts/e2e-test.ts L1934「删有款的单
  被拦住」）走同一份 core 已锁。审计定位本是接线锁不是断言强度锁，不算缺陷（见挑刺 3）。

### (b) orders/lastExchangeRate——全局最近一次下单汇率锁：**supertest 坑描述属实，实弹四发全中**

- **实现**（core/orders.ts L2949）：`SELECT exchange_rate FROM orders ORDER BY updated_at
  DESC, id DESC LIMIT 1`——不带参、全局取最近一张单的汇率；控制器（orders.controller.ts
  L195-198）直接把 `Promise<number | null>` 顶出去——顶层原始类型 JSON。
- **实弹四发**（同一临时实例，含跨值与回落）：
  1. 建单 rate=7.2 → `lastExchangeRate` status 200，**text=`"7.2"`、body=`{}`（keys 空）**——
     「supertest 顶层 number 不进 body、只有 text 有值」的坑描述逐字属实；
  2. 再建一张 rate=7.5 的单 → 返回 **7.5**——证「全局最近一次」，不是按客户、不是缓存；
  3. 删掉 7.5 空单 → `get` 200 text=`''`（顺带复核 delete 半边）；
  4. 再查 → **回落 7.2**——证「最近一次下单」语义而非写死。
- e2e 断言走 `Number(text) === 7.2` 且断言名里带上坑的注记（「顶层原始类型 JSON 走
  text 断言」）——研发留档 out/http-r102.log / r102b.log 两轮红（extra 先 `{}` 后
  `{"status":200,"text":"7.2","body":{}}`）与叙事相符，坑记进断言名属实。

### (c)(d) addItem / samples/list——经 test:all 日志逐条 ✓ 复核（未实弹）

- `orders addItem 单条落库（与批量 addItems 并存的正门）` ✓：addItem 后 get 复核

- 抽验要求是「四条抽两条」，两条实弹抽的是 delete / lastExchangeRate（合同层最深的

   会对不上。建议下轮在 backend-plan R102 条目补一句勘误注记（照 R100 的做法）。
2. **README 断言规模漏同步**：README.md L262 仍写「HTTP 冒烟 241 项」，本轮实际 245。
   R101 同步了 README，R102 漏了这一行。一行字的事，下轮补上；本轮无渲染层改动，
   AGENTS 规则一的 README 义务严格说只绑界面更新，但数字既然变了就该跟着走。
3. **delete 的 HTTP 面只锁了「空单可删」半边**：「任一 blocker 拒删」半边靠桌面 e2e
   L1934（走同一份 core）托底，HTTP 面无锁。与审计自述「接线锁，不是断言强度锁」
   的定位一致，不算缺陷；将来若做 HTTP 面扩面，可把 blocker 拒删的中文报错也锁进
