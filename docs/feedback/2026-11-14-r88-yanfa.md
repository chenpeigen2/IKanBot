## 一、做了什么

1. **IPC 三层接线审计入库**（已做并验过）：`scripts/audit-ipc-wiring.cjs`（npm run audit:ipc）
   把 R83 复验人工做的三层核对自动化——主进程 handle（扫整棵 electron/ 树）/ preload call
   面（字符串感知剥注释后提取）/ REMOTE_ROUTES / server 控制器路由逐层对表。硬闸三条
   （任一不满足 exit 1）：preload 调的通道必须有 handle（点到就现场报错类 bug）；远端转发
   通道必须有 handle；远端路径必须存在于 server 控制器（远端打空气类）。软清单两条人审：
   死通道候选、本地独有通道（31 条，覆盖率口径的本体——shell/app/mode/updater/images
   本机操作/backup 本机/导出落盘/单据本机/窗口打印）。
2. **审计工具自己的红验证（真抓过）**（已做并验过）：首版只扫 electron/ipc/index.ts，
   audit 报出 5 条 updater 通道「preload 调了但没有 handle」——查实注册在
   electron/services/updater.ts（同一个 handle 助手）。这是工具口径漏洞不是产品 bug，
   但它证明了硬闸 A 的判定逻辑能真报红（不是永远空的假锁）。修工具扫全树后 131↔131
   对齐、exit 0。
3. **http 审计四口径加强**（已做并验过，R87 复验小账清偿）：① 域目录多 controller 文件
   全扫；② @Delete/@Patch、双引号装饰器同扫；③ 字符串感知的注释剥离（check 名里的路由
   字面量算锁——那是真断言的名字；纯注释里的不算）；④ **反方向对表**：冒烟正文里的
   /api|/healthz 字面量逐个反查控制器，不存在的报「打空气的死测试」（allowlist：/healthz、
   /api、故意 404 负向测试用的 /api/no-such-route、参数前缀 /api/files/images/、
   /api/export/）。反方向逻辑自证能抓（假路由 dead-detected=true、真路由 passes=true）。
   终态：108/108 + 反方向零死路由。

### 二、返工明细（代码 diff 逐行）

1. audit-ipc B2 正则：`(?:['"])([a-z]+:[a-zA-Z0-9]+)\1\s*:\s*\{\s*path:\s*(['"])([^'"]+)\2`
   → `(['"])([a-z]+:[a-zA-Z0-9]+)\1\s*:\s*\{\s*path:\s*(['"])([^'"]+)\3`（引号组改捕获，
   path 回引 \3）。
2. audit-http 反方向 allowlist：原 `ALLOW=[…].some(a => lit===a || lit.startsWith(a))`
   → 改双列语义：`ALLOW_EXACT`（`/`、`/healthz`、`/api`、`/api/no-such-route`——**精确匹配**）
   + `ALLOW_PREFIX`（`/api/files/images/`、`/api/export/`——尾斜杠前缀匹配）；query 串字面量
   先截 `?` 再对。
3. **handleSync/sendSync 旁路收编**（复验顺账建议，采纳）：handle 扫描正则 `\bhandle(?:Sync)?\(`
   （主进程侧），preload 侧补 `sendSync\(` 提取——images:baseDir（ipc/index.ts:495 +
   preload:212）从此可见：**132/132**（原 131/131 是静态盲区，覆盖率分母 122 = 132 − mode 5
   − updater 5，正好对上）。
4. 软清单 D 文案修正：不再把 32 条说成「22 条口径本体」，写明「22 条业务未覆盖是这里的子集，
   另含 mode:/updater: 前缀豁免」。
