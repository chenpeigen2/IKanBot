## 二、逐项亲验记录

### ① 白名单与只读口径——放行实锤，注释把边界说死了

`git show HEAD:core/backup.ts:325-326`：`RESTORE_ALLOWED` 含 `'migration-report.json'`，注释原文
「打包时现算的搬迁对账——恢复侧只读它做逐项对，不落盘不参与换库」。该 entry 不进换库白名单之外
的任何落盘路径。报告说的红验证（首跑白名单没认识这个 entry → 恢复被拒 → 「一步都没动时也明说
数据原样」红）与这个结构吻合：守门白名单确实需要本轮这行改动才认识新文件，结构性红成立
（未用 stash 法重演，缺口形状与守门机制我已从代码两侧确认）。

### ② hooks 复核——可选钩子 + 两头实现 + 算不出来不拖死备份

- `core/backup.ts:64`：`BackupHooks.migrationReport?()`——**可选**（`?`），钩子不提供就是老行为；
- 桌面实现：`electron/services/backup.ts:88` `migrationReport: () => migrationReport(coreDb)`；
  服务器实现：`server/src/backup/backup.service.ts:117` `migrationReport: () => migrationReport(this.db)`
  ——两头同一份 core/migrationReport（与客户页「可用预收」同源那套）；
- `writeBackup`（164-172 行）：`if (hooks.migrationReport)` → try → entry 追加；
  **catch → `console.warn('[backup] 搬迁对账没算出来，本包不含对账：…')` → 包照打**——
  算不出来不拖死备份的分支真实在。

### ③ diffMigrationReports 纯函数 + 两头组装——对得严，翻脸翻得准

`core/migration.ts:123`：逐项对表行数（只记有差的表）、收款合计、单号两计数、抵扣台账、
逐客户余额行（sameRows），全零差才 `ok=true`。两头壳层组装同构：

- 服务器（`backup.service.ts:170-174`）：`before = packedMigrationReport(packPath)`（读包内
  migration-report.json）→ `withDiff = {...report, diff: diffMigrationReports(before, report)}`
  → **持久化进 last_restore_report**（带 reportedAt）→ restore 响应带回；
- 桌面（`services/backup.ts:157-160`）：本机恢复同样组装（读包 + 现算 + diff）；
  包里没有对账（老包）→ 只给 report 不硬造 diff；对账算不出 → 不影响恢复本身。
  core 的 restore 返回结构没动——组装全在壳层，恢复闸门不受影响（与报告说法一致）。
