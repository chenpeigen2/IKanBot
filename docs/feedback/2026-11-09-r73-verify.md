## 二、逐项亲验记录

### ① 自验复核（本轮的命）——「同一道闸」是真的同一道

`git show HEAD:core/backup.ts` writeBackup 内（183-186 行）：

- `verifyZip`（包结构）之后、`renameSync`（落盘）**之前**：
  `const selfCheckEntry = entries.find((e) => e.name === 'ikanbot.db')` →
  `inspectRestoredDb(selfCheckEntry.data, …)`——`inspectRestoredDb` 正是恢复路在用的那道
  探针闸（自检 quick_check / 版本守卫 / 核心表，R67 时我锤过它与 inspectBackup 共享
  assertDbProbeUsable）——**备份自验与恢复闸门逐字同一道闸**，不是另写一份校验。
  字节在手零额外读，动机成立。
- **失败语义成立**：闸不过 → throw → 外层 catch `unlinkSync(temp)`（坏包不落盘、不进备份列表）
  → `await hooks.markFail(msg)` 且 markFail 自带 try/catch（记原因这一步坏了不顶掉原始失败）
  → `throw e` **原样往外抛不重包**（注释引了 r61-verify 的账：重包会丢 .code/.path，EACCES
  会被服务器映射成「服务器内部错误」五个字——这条与 df38833 的修法一脉相承）。
- 落盘之后的善后（prune/markOk/降级留痕）隔离在另一个 try 里，任何一步坏了不许把成功说成失败
  ——成败边界画得干净。
- 「红验证不可达」的诚实标注我认：正常 snapshotDb 的产物必然过闸，红态需要「写包时库字节损坏」
  的未来回归才触发——性质是回归锁，与 R72 先例同款口径。

### ③ 审计抽查 3 条——三条判定全对

- **export:csv**（判定：已有远端分支，远端由后端算 CSV 本机另存）：`electron/ipc/index.ts:595`
  ——`isRemoteMode() ? await remoteExportCsv(kind, filter) : dashboard.exportCsv(...)`，
  远端 CSV 由后端那份账算出，本机只走另存对话框写文件；注释还把为什么转发器不代劳讲清了
  （export: 前缀本机独有）。**判定对。**
- **backup:lastResult**（判定：跟备份发生地走）：`:586` ——远端模式读**服务器 settings** 的
  lastBackupAt/lastBackupError（备份发生在服务器），本机模式读本机。**判定对。**
- **window:print**（判定：天生本机）：`:762` ——`BrowserWindow` 的 `webContents.print(...)`，
  打印子系统就在本机桌面环境里，服务器没有窗口可打。**判定对。**

三条抽自三类不同判定桶（自定义组装 / 已有远端分支 / 原生 OS），抽样覆盖面成立，
「M2 业务通道迁移实质完成、99/121 只数转发表」的结论我认。

## 三、新发现 / 疑点

1. **README 断言规模第二次漏刷**（2507 那次记过账、R71 补上，这轮 2516/223 → 2517/224 又没动）：
   连续两轮自动化报告的事项清单里都没有「README 更新」这一项——自动化流程生成报告时把
   「刷 README 数字」这一步漏出清单了。一次是手滑，两次是流程缺步。建议把「断言数字 → README
   231 行」写进自动化收尾清单；本轮我先记账，数字以我的复验报告与 backend-plan 为准。
2. **回归锁的名称没带 R73/读回自验关键字**：任务 grep「R73」在日志里落空（断言落在既有「备份」
   节、名字是「成功备份的包能过恢复侧同一道探针闸」）。锁本身是好的，但「R73 回归锁」想被后来人
   grep 到，断言名或注释里最好带轮次号——源码注释带了、日志输出没带。极小，提一句。
3. 自验闸与恢复闸共享 `inspectRestoredDb` 的一个隐含契约：备份时**不弹**「已在恢复」的检查
   （restore 分支才有 restoring 早退）——当前 writeBackup 与恢复互斥由调用层保证，无冲突，
   但将来若有人在恢复途中触发自动备份，会走一次探针开库。当前时序（自动备份只在启动与每小时，
   恢复互斥在 ipc 层）够用，记一笔备查。
