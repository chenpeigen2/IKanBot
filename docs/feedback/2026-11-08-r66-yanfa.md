# R66 研发报告 —— 整库搬迁最后一公里：本机包上传 + 搬迁对账

日期：2026-11-08。基线 v0.5.7。每条标注「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **服务端上传口**（已做并验过）：`POST /api/backup/upload`（octet-stream，鉴权同备份簇）。
   `core.importBackupZip`：字节落进服务器备份目录（uniqueBackupName 防撞名）→ 走与「列表里选
   一份」**完全同一条** inspect 闸门（zip 结构、quick_check、版本守卫——v25 包被老程序恢复照样
   被那道人话守卫拦）；验不过的包当场删，列表里不留垃圾。恢复仍走既有 `/api/backup/restore`，
   两步分开、恢复前保留「查看摘要后确认替换」。这是 R61 挂账「服务器备份包没有上传本机 zip
   去恢复的口子（搬迁走第七节工具，M5）」的转实做——搬迁不再缺最后一公里。
2. **桌面接线**（已做并验过）：远端模式下 `backup:inspect` / `backup:restore` 收到**本机存在**的
   路径（pick 的对话框永远在本机）→ 先上传（同一本机路径会话内缓存：界面「先看摘要再确认恢复」
   是两次调用，不重传），之后全链走服务器路径与既有闸门。服务器自己的包原样转发；本机模式零改动。
3. **搬迁对账**（已做并验过）：`core/migration.ts` `migrationReport(db)`——12 张核心表逐表行数 +
   三个口径指纹（收款合计 SUM(payments.amount)、单号唯一=orders 行数对 DISTINCT(order_no)、
   抵扣台账合计 SUM(reversed_at IS NULL)）。server 的 restore 响应带 report：行数对不上、
   单号重复就是搬坏了，别让「恢复成功」替人背书。
4. **测试**（已做并验过，红→绿）：
   - HTTP 五条：上传 401、坏字节人话拒绝（「这不是一份 IKanBot 备份包」）、整库包上传成功带摘要、
     走既有闸门恢复成功、恢复响应带对账（表行数/收款合计/单号唯一/台账合计）。
   - 双模式两条真演练：服务器包字节复制成本机文件伪装「老桌面导出的整库包」→ 远端 inspect
     自动上传（摘要是服务器那份）→ 远端恢复成功（缓存命中不重传）且带对账。
   - 桌面 e2e 九条：对账口径指纹用「前后差一张」锁死（整库 SUM 会被全套测试垫底，绝对数不稳，
     增量才是搬没搬对的判据）+ 核心表 12 张一张不缺 + 接线检查两条。
   - **红验证**：暂存实现跑 server 套件——死在路由计数守门（107≠108），搬迁段根本到不了 404。
     路由清单是结构性的红闸门。恢复后全绿。
5. **记账修正**（已做并验过）：「下一刀」的旧数过时（images 簇远端链路此前轮次已落地），
   复核更新为 108/121；剩余通道里 window:/shell:/app:/mode:/updater:/backup:pick|reveal
   是原生对话框/窗口/更新器，天生本机不该上后端。
6. **README**（已做并验过）：断言规模 2497/142/76/219。
