## 二、大件：M4 并发第一片 —— 已做并验过

按 `docs/backend-plan.md` 第四节的既定方向落最小闭环，两片都是「SQLite 与未来的 MySQL
同一套语义」：复查都在 transact 内做，不靠前端预检。

### ① 写冲突检测（乐观锁）—— 261dcee

- 订单/商品/客户三张热表的更新走 `UPDATE … WHERE id=? AND updated_at=?`，
  affected 0 行即「别人刚改过」→ `BizError` 409 + 中文话术；
- 桌面三处编辑（订单编辑弹窗、商品编辑、客户编辑）把读到的 `updatedAt` 随保存带上；
  不传 `expectedUpdatedAt` 的老调用不受影响（HTTP 有断言锁这条）；
- HTTP 冒烟锁了完整四步：窗口 A 拿读单时的 `updated_at` 存成功 → 窗口 B 拿旧的被拦 409 →
  B 刷新后重存成功（矛盾解开不卡死）→ 老调用不受影响；e2e +13（含桌面接线检查）。

### ② 收款幂等 —— 8b741c7（本轮补完，TDD）

- 新迁移 **v24**：`request_dedup(request_id PRIMARY KEY, kind, result, created_at)`——
  PRIMARY KEY 就是唯一索引，MySQL 侧同语义（真撞上时第二笔整体回滚，绝不落两笔钱）；
- 三个落钱入口收**可空** `request_id`：订单收款（`addPayment`）、打样费收款、预收退款；
  复查在**事务内、排在所有守门之前**——重放要拿回第一次的结果，而不是被水单查重、
  「已收齐」这些门拦成报错；落账成功后把结果快照（单据详情 / 余额）存进表，
  重放的人看到「第一次到底落了什么」；
- `request_id` 为空（老调用方、水单拆分收款、脚本/导入）不检查，行为照旧；
- 桌面端 `newRequestId()`（`ui.tsx`）生成，随请求带上；**成功之后才换号**——
  双击被按钮 busy 拦住，网络超时重试沿用同一个 id 被服务端幂等兑底；
- **红验证（本轮亲手做的）**：把 `findReplay` 暂时改成永远返回 null 重跑 e2e——
  重放当场撞水单查重（BizError「这张单上已经登记过流水号…」），测试确实会红；
  恢复实现后 2347 全绿。红绿都有据。
- e2e +21：订单收款同 id 重放只落一笔、重放返回第一次的金额、不同 id 照常落账、
  不传 id 走老路；打样费同 id 重放只落一笔；预收退款同 id 重放余额只减一次（40−30=10）、
  重放返回第一次的余额快照；桌面三处接线检查（带 requestId、成功才换号）。
  HTTP +2：同 id 重放两次都 200 且只落一笔。

## 请文娟复验的重点

1. **双击收款**：登记收款时连点两下「登记收款」——应该只落一笔（按钮 busy 本来就拦一层，
   现在就算程序重试也不会落第二笔）。
2. **断网重试**：登记收款时如果卡了一下、界面报错了，别急着重新点——先看收款记录里
   是不是其实已经记上了；重试同一次操作不会再多记一笔钱。
3. **两个人同时改一单**（如果你们两个人同时用）：后保存的那个会看到「这条记录刚被别人改过，
   请刷新后再试」，刷新改完再存就好，不会把别人的改动悄悄盖掉。
4. **编辑订单改到一半关程序**：和 R61 新建订单一样，重开编辑弹窗会问你恢复不恢复上次没存的稿。
