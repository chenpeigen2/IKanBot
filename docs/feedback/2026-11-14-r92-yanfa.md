# R92 研发报告 —— 锚点竞态修复：等两张卡的数据到位再滚

日期：2026-11-14。基线 v0.5.33。每条标「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **锚点竞态修复**（已做并验过，R91 复验实测竞态清偿）：R91 复验用浮层铁证实测——
   锚点 effect 是一次性 150ms 定时器 + early return + `?.` 静默吞，settings 数据晚到时锚点
   还不在 DOM，直进 **10 跑 7 落**（scrollTop=0 anchor=Y），远端模式 settings.get 走 HTTP
   暴露面更大。修法：effect 依赖 **[s, source]**——两张卡的数据都到位、布局长到最终高度
   再滚（开发中实测只等 s 的版本会先滚到一半、来源卡随后长高把锚点顶离视口顶，遂把
   source 也入闸）+ 一次性 `scrollDoneRef`（防 s 后续刷新把用户拽回备份卡）+ 锚点元素
   `scroll-margin-top: 70`（topbar 不遮挡标题）。
2. **稳定性实测**（已做并验过）：同口径直进（`shot.sh '/settings?scroll=backup'`、无点击、
   纯滚动验证）修复前 6 跑 3 落 → 修复后 **6 跑全中、落点逐像素一致**（R91 复验 10 跑
   3 中）；抽 3 张读图核对（#1/#2/#5 同几何）。截图 1 张入库 docs/ui/r92/。
3. **e2e 补锁**（已做并验过）：「锚点滚动等两张卡的数据到位再滚」——effect 依赖 [s, source]
   + scrollDoneRef + 双数据闸三件同在（源码锁）。红验证：锁写在实现前实跑 ✗ 红（R91 两条
   照绿——锁独立性也对）、实现后 2560 全绿。
