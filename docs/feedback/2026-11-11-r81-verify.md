## 三、逐项亲验记录

### ① 上限收紧——照做了，数字对

`pageMs2 < 500`，深翻页新断言也用 500ms。我 R80 建议的就是 500ms（实测 9ms 的 ~55 倍余量，
慢机器按 5 倍估也安全；按我探针曲线 ~0.011ms/单外推，500ms 约在 4–5 万单 binding，与研发
记账「5 万单量级」一致）。这条是本轮最实的一条清偿。

### ② 深翻页——新断言是真的，但「改测」没改干净

新断言 offset 400 在 561 行内，`rows === 20` 且 <500ms，绿——「能出且非空」这次真验了内容。
但旧的「深翻页（第 8 页）也能出且耗时同量级」**原样留着**：offset 已经没有 4000 的调用了，
它量的是同一个 offset 400 调用的耗时（lastMs 对同一 t2），名字「第 8 页」已无对应物，
3000ms 上限也过期（同一个调用新断言已用 500ms 收紧）。「改测」应当是替换，实际是并存，
e2e +1（2540→2541）正是加而不删的结果。

### ③ 绿跑留档——还是没做（本轮打回的主因）

我 R80 点名的缺口：`check()` 通过时只打 `✓ 名称`，detail 只在失败时出现——所以基线 ms 数
在绿色通过时**不落在任何地方**。我当时给了两条路：perf 断言通过时也打印 detail，
**或**把数值写进 backend-plan 记账。R81 两条都没走：check() 本体未动（diff 与 HEAD 原文
双确认），原跑（全绿 2541）日志从商品库到 HTTP 冒烟没有一处 ms 数。研发把 ms 塞进了
detail 参数（首页断言此前没有耗时，这次加上了）就记成「绿跑的 ms 数也进 check detail」
「已做并验过」——detail 参数里带 ms ≠ 绿跑留档，绿跑根本不打 detail。backend-plan 还把
「③ detail 恒带耗时（绿跑也留档 ms 数）」记成了完成态，**这条记账是假的，需要改**。
顺带：新深翻页断言连 detail 参数都没有——失败时连 ms 都看不到，与「恒带耗时」自相矛盾。

**基线数值留档（仍由本报告承担，R81 代码实态，/tmp 副本跑出）**：561 单（rows 61→561）下
first 8ms / second 9ms / 深翻页 offset 400 为 8ms（新断言无 detail，此值来自同调用的旧断言
detail）——与 R80 的 9/9/8ms 同量级，500ms 新上限余量约 55 倍。

### ④ 注释修正——对，与实现和我上轮的实证完全吻合

core/orders.ts:464「total 的口径（R80 复验实证）：只排除作废（void）——草稿/失效都计入
行数与 total」对照实现：`total = sorted.length`（全筛选集），排除只靠 `listWhere` 默认分支的
`o.payment_status != 'void'`——我 R80 逐状态插库实证（draft 计入 0→1、expired 计入 1→2、
void 不计入 2→2）就是这个映射。e2e 注释同步改，且「全表 COUNT 与 total 差出的 5 张是
前面段的作废单」与 void-only 排除自洽。这条修正把 R80 我标的两处机制错注都清了，干净。
