## 四、实现读核（四件套 + 回拉防护）

Settings.tsx:238-245，四件全在且逻辑自洽：

1. **依赖 [s, source]**（:245）——两张卡的数据都到位、布局长到最终高度才滚；R91 挑刺 3 的
   「来源卡随后长高顶走锚点」次生窗口与一次性 150ms 定时器（旧 :233-237）一并清掉。
2. **scrollDoneRef 一次性闸**（:238/240/243）——置位在 `scrollIntoView` **之前**，此后 s/source
   任何后续变更（保存设置的 setS、登录失效广播里的 loadSource、切模式 setSource）都被首行
   `if (scrollDoneRef.current) return` 拦下——**用户不会被拽回备份卡**。React StrictMode 开着
   （main.tsx:11），effect 挂载双跑也被同一行拦住，一次性语义两种环境都成立。
3. **双数据闸 `if (!s || !source) return`**（:242）——s 晚到时不再赌 150ms 定时器，等下次数据
   变更自然重试；锚点 div 在 `!s` 渲染闸门（:380）之后无条件渲染（:778），双闸过了锚点必在
   DOM，`?.` 不再有静默吞失败的实害。
4. **scrollMarginTop: 70**（:778）——在 DOM 上、参与 scrollIntoView 计算；当前几何下终位由
   钳位决定（探针实证，口径见挑刺 1）。

回拉防护的边界如实记一笔：数据未齐时用户已进页面开始读、数据到位后被拉下去**一次**——这是
本功能的设计本意（「进来直达备份卡」），窗口 ≤ 数据到达耗时（本机亚秒级），且 ref 保证只发生
一次；与修复前「数据晚到就永远不滚」相比是净收益，不必动。

## 七、挑刺（均非打回项）

1. **scroll-margin-top:70 的机制说法与实况有偏差**：r92 README 与研发报告写「备份卡贴视口顶
   （scroll-margin 生效，未被 topbar 遮挡）」——探针实证终位由 max-scroll 钳位决定（st=max=1525，
   目标 1633 超出被钳），margin 在当前页面几何下不改变终位，「未被 topbar 盖」是钳位的副产品。
   行为正确且稳定，但机制描述应修正，免得后人把 margin 当落点保证。
2. **「落点逐像素一致」字面口径过强**：整 PNG md5 因文字 AA（≤3/255）与「X 分钟前」相对时间
   跨分钟变化而不逐字节相同；几何口径（st/aTop）才成立。建议以后这类断言写「落点几何逐跑一致」。
3. **R92 补锁仍是源码串锁**：锁「四件套字符串同在」不锁「滚没滚、滚到哪」——时序行为串锁天然
   不可见（R91 挑刺 2 现状维持），本轮以 10 连跑实拍 + 探针补位。
4. **真库 md5 与 R91 记录值不同**：R91 记 `a38bc8df2964251f76917642a7db9443`，今日
   `c2c9658d570cb69941385951dfe465a5`（mtime 17:13:16，早于我开工）——两轮之间有东西碰过真库
   （研发本机实跑应用的可能性最大），我无法归因。我的复验窗口内前后一致、11 次启动全走副本。
   记账备查，请研发下轮顺带说明。
5. **观察一笔（非缺陷）**：一次性 ref 只防「重复拽人」，不防「数据到位那一下的单次拽人」——
   数据晚到且用户已开始读时会拉下去一次。设计本意如此、窗口亚秒级，量级远小于修复前的
   「永远不滚」，不必动。
