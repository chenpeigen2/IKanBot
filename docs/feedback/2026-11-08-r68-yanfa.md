# R68 研发报告 —— 恢复对账收尾三件（逐客户预收余额 / 持久化 / 设置页对账卡）

日期：2026-11-08。基线 v0.5.9。每条标注「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **逐客户预收派生余额**（已做并验过）：migrationReport v2 带非零余额行（客户/币种/可用），
   余额逐个调 money 域的 `customerCreditBalance`——与客户页「可用预收」同一份算法，不另写一份
   （第七节第 2 条最后一小项）。候选客户 = 收过钱的单的客户 ∪ 抵扣台账有动静的客户；
   第一版只查台账、漏掉了「刚多收还没用」的客户，**断言当场抓住**（creditBalances 为空），
   改成并集后绿。server e2e：造 1000 多收（无明细单，全额进预收）→ 打包 → 恢复 → 余额
   出现在客户名下（available 1000, USD）。
2. **恢复对账持久化**（已做并验过）：恢复完成后写 settings `last_restore_report`（带
   reportedAt），新通道 `backup:lastReport`（本机读本机、远端读服务器；覆盖率 99/121）。
   本机模式恢复成功那一刻进程退出（afterRestore relaunch+exit），对账由**重启后的启动流程
   补算**（`settleRestoreReport`）：pending 标记放 **userData 根目录小文件**——第一版放
   settings 被实拍踩坑（恢复把整库换成包内容，包打在标记写入之前，标记必被洗掉）。
   桌面 e2e 锁「pending → 补算 → last_restore_report → 清标记」全链。
3. **设置页对账卡**（已做并验过）：备份卡下亮「最近一次恢复的搬迁对账」——12 表行数一行排开、
   收款合计、单号 4 / 去重 4（平）、抵扣台账合计、客户预收余额逐客户；文案把「对不上就别录单，
   先来问」说在前头。截图 2 张入库 `docs/ui/r68/`（基础形态 + 带客户预收余额行形态）。
4. **吞错修正（R67 边角）**（已做并验过）：远端 inspect/restore 区分「服务器自己的包」与
   「本机包」改用**服务器备份列表认领**——列表里有原样用（inspect 真错误原样透传，不再被
   「服务器上没有」吞）；列表外本机有才上传。双模式锁：「本机『未来包』上传被版本守卫拦时，
   桌面拿到『请先把程序升级』这句人话」。诚实标注：吞错场景（服务器列表里有 future 包 +
   existsSync false）在同机双模式无法真实复现，红验证不可达——判据替换消除该类路径，
   透传行为有断言（修前修后都绿，不算红验）。
5. **顺手修**（已做并验过）：`scripts/shot.sh` 失败分支 `（rc=$RC）` 的多字节变量名解析报错
   （`${RC}` 加花括号）——今天首次走进「截图失败」分支才暴露的存量 bug。
