## 三、新发现 / 疑点

1. **`order-detail-stale.png` 与 `order-detail-reload.png` 这对对照图摆拍糊涂，README 的说明与图对不上**
   （证据质量问题，功能本身没问题——我已连拍证实）。两个硬伤：
   - stale 图里页面主体显示的是**新值**「R63-别的窗口改过」，但详情页主体根本不会实时变（我连拍证实
     显示的是载入那一刻的旧值）；README 却解释成「列表数据是实时的，提示说的是你手里这份快照」——机制说错了。
   - reload 图里 PO 显示「R63-详情页演示」，比 stale 图的值还**旧**（重新载入不可能把数据倒回去）。
     真相是两张图分两次拍：reload 那次先把 PO 又写回「R63-详情页演示」再重载。README 说「同一详情页……
     客户 PO 仍是新值」——两张图拼不成一个连续故事，谁对照谁都会糊涂。**下一轮请把这对图在同一个
     连续会话里重拍**（拍法我这轮已经趟通：写一笔 → focus → 截第一张 → 点重新载入 → 截第二张）。
2. **「黄条」其实没有黄**：全仓库没有 `.stale-hint` 的任何 CSS 规则，弱提示渲染出来是一行**裸文本**
   （截图可证，我自己拍的两张也是）。报告、README、界面文档都叫它「黄条」，名不符实。
   不拦操作的功能语义是对的，但连个警示底色都没有，扫一眼容易当普通说明文字略过。
   要么补样式（`--warning-soft` 那套现成的），要么把「黄条」的说法改掉。
3. **报价/打样的 CAS 没有「不传凭据走老路」显式断言**（订单有这条）：两张单是本轮新接的锁，
   老调用兼容只靠同款语义推定。风险很低（同一套 `expectedRowVersion` 空值即跳过的代码路径），
   记一笔，下轮顺手补一条即可，不算窟窿。
4. **研发的红验证（还原 shipping.ts 恰好两条变红）我没有重演**——那是他的 TDD 纪律账；正向侧
   两条出货断言在我跑的 e2e 里是绿的，`core/shipping.ts:142` 的 bump 行真实存在，我认账不追打。
