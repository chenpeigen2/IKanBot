# R67 研发报告 —— R66 复验小账清偿 + inspect 版本守卫真窟窿

日期：2026-11-08。基线 v0.5.8。每条标注「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **真窟窿：inspect 不做版本检查**（已做并验过）。给上传版本守卫写专属断言时实锤：
   `inspectBackup`（上传/列表摘要把守的闸门）原先只查 zip 结构、quick_check（间接）和核心表
   计数，**不查 user_version**——版本守卫只在 restoreBackup 那条路。搬上来的「未来包」只要有
   核心表就能过摘要、拖到恢复才被人话拦。修法：抽出 `assertDbProbeUsable(database)`
   （quick_check + 版本守卫，话术与 restore 路逐字共享），inspect 与 restore 两条路同一道闸。
   红验证顺带成立：修前同断言死在「这个备份包打不开来看：no such table: orders」（守门缺失
   的直接证据），修后是「这份备份来自更新的程序版本…请先把程序升级到该版本或更高」。
2. **判据修正：服务器自己的包不被误传**（已做并验过）。远端 inspect/restore 区分「服务器自己
   的包」与「老桌面带来的本机包」，原判据 `existsSync` 在同机部署（mode-test 实锤：服务器备份
   目录就在本机盘上）会把服务器自己的包误传一份。改成**服务器先认领**（inspect 探针，快）：
   认领成功原样用；认领失败而本机确有此文件 → 上传（会话内缓存不重传）；两边都没有 → 人话。
   双模式新断言：imported 包恰好一份、不含 manual 误传副本。
3. **上传缓存行为断言**（已做并验过）：同一本机包「摘要 + 恢复」两次调用只上传一次。
4. **计数口径**（已做并验过）：R66 报告「桌面 e2e 九条」改注八条（+1 是方言照妖镜对
   migration.ts 自动多扫的 5 条，增量账本身准）；R66 复验报告加 R67 追记（三条小账去向）。
5. **记账 + README**（已做并验过）：backend-plan.md 新增 R67 条目；README 断言规模
   2497/143/76/220。
