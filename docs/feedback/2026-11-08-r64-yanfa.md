# R64 研发报告 —— 水单拆分收款（batchAddPayments）补幂等键

日期：2026-11-08。基线 v0.5.5（R63 当轮发布后接着做的小轮）。每条标注「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **整批幂等键**（已做并验过）：`batchAddPayments(entries, requestId?)` 收可空键——拆分收款是
   「一张水单拆到 N 张单」的**同一个动作**，键盖整批、不做逐行去重（逐行键会给「重试只补失败
   那几行」的半截账留缝）。重放排在所有守门之前，拿回第一次的整组结果快照；快照与落账同事务
   （复用 R62 的 `request_dedup` 表，kind=`batch_payment`）。不传键的老调用照旧。
2. **全链管道**（已做并验过）：core → electron/ipc → preload → 远端转发（`args: ['entries','requestId']`）
   → server 控制器 → NestJS 服务 → `src/shared/api.ts` 类型，一处不落。
3. **桌面接线**（已做并验过）：客户页水单拆分弹窗打开就 `newRequestId()` 发号，提交随批带上；
   失败重试沿用同一个号（第一次其实落了账、响应丢了的情形，重试拿回服务端快照而不是被水单查重
   硬顶回来）；保存成功整份清掉，下次打开换新号——与 R62 三个落钱入口同一套规矩。
4. **断言**（已做并验过，红→绿）：
   - 桌面 e2e 新节「R64：水单拆分收款幂等（整批一个 request_id）」八条（六条行为 + 两条接线）：首次落两笔、同键重放
     拿回第一次整组结果且流水不翻倍、换新键的新水单照常落、老调用不传键不受影响、接线检查两条。
   - HTTP 新增三条：整批落账、同键重放不翻倍、换新键照常落。
   - **红验证**：实现落地前跑同一段——同键重放没被幂等层接住，直接撞水单查重硬报错
     （「同一张水单不能记两次…」整批回滚），测试当场死在这——这正是这颗键要防的真实故障
     （第一次其实已落账、响应丢了，人重试一次被查重顶回来）。实现后全绿。
   - 测试自身先写错过一处：换新键时复用了同一个流水号，被水单查重拦下——那道闸门是对的，
     新键必须配新水单号，已改测试并把这条写进注释。
5. **记账 + README**（已做并验过）：backend-plan.md 新增 R64 条目；README「收款」补水单拆分
   入口、断言规模刷成 2478/140/76/214。
