# R70 研发报告 —— 搬迁对账进包：包与恢复两头自动对平

日期：2026-11-09（自动化首轮，接 R69）。基线 v0.5.11。每条标注「已做并验过 / 已做但没验 / 没做（原因）」。

## 一、做了什么

1. **搬迁对账进包**（已做并验过）：BackupHooks 加可选 `migrationReport()`（桌面调 coreDb、
   服务器调 this.db——与客户页「可用预收」同一份算法），writeBackup 在收集条目后把对账作为
   `migration-report.json` 进包；算不出来不拖死备份（console.warn 后包照打）。恢复白名单
   （RESTORE_ALLOWED）放行该文件——只读它做对账，不落盘不参与换库。
2. **diffMigrationReports 纯函数**（已做并验过）：before（包里「导出那一刻」）vs after（恢复后
   现算）逐项对——表行数、收款合计、单号计数、抵扣台账、逐客户余额；全零差 ok=true。
   恢复就是把库换成包内容，两份必须全零差，对不上说明包或恢复有一头坏了。
3. **壳层组装**（已做并验过）：服务器 restore 响应带 `report.diff`（并持久化进
   last_restore_report）；桌面本机 `restoreBackupWithReport` 同样组装（读包 + migrationReport +
   diff）。core 的 restore 返回结构未动——组装全在壳层，restore 闸门不受影响。
4. **三笔表述账**（已做并验过，R69 复验挂账）：services 注释旧名改名（restore-report-pending
   文件）、seed 空防键补说明（全仓库无写入者，防将来有人用；真标记是 userData 文件，seed
   不碰也不该碰）、R69 报告计数口径更正小注（「两条」实为 7 条，增量 +7 本身精确）。
5. **测试**（已做并验过，红→绿）：桌面段——包里带对账 entry、包内行数与打包那一刻的基线对齐、
   diff 纯函数「同账全零差 / 差一笔就翻脸且指出差在哪（orders 差 1、收款差 72）」、server 接线
   grep；HTTP 段——恢复响应带 diff 全零差。**红验证**：首跑时恢复白名单把 migration-report.json
   当不认识文件拒（「一步都没动时也明说数据原样」红），白名单放行后绿——守门的白名单需要
   认识新 entry 是本轮改动的直接证据。

## 三、没做什么 / 挂账

1. 对账 diff 的设置页呈现（对账卡加「包内 vs 恢复后」两列对比块）：没做——diff 数据已在
   restore 响应与持久化里，UI 呈现留下一片（要动 UI 就要带截图矩阵）。
2. 打包对账与库快照的严格同事务一致性（VACUUM INTO 快照内算）：没做——两次查询之间有间隙，
   切库窗口本来就停写（第七节），记账接受；要严格可把 report 塞进快照流程。
3. MySQL 侧原语真实现与逐表搬运——按第七节留 M5（无可测环境）。
