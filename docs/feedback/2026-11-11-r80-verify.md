## 三、性能合理性评估（本轮复验重点）

**结论先行：3 秒上限太松，锁不住缓慢劣化，建议收紧到 500ms。**

1. **余量 333 倍**：实测 8–9ms 对 3000ms 上限。哪怕劣化 30 倍（270ms，业务上已经感知卡顿）
   照样绿灯。上限真正 binding 要到约 25 万单（见下条推算）——这台账本永远到不了。
2. **规模曲线（独立探针，每档预热后连测 5 次）**：

   | 总单量 | 首页耗时（ms，5 次） | 深翻页 offset 4000 |
   |---|---|---|
   | 500 | 11, 8, 9, 7, 7 | 7ms，**返回 0 行** |
   | 2000 | 24, 23, 26, 23, 24 | 22ms，返回 0 行 |
   | 6000 | 61, 68, 70, 67, 64 | 61ms，返回 20 行 |

   近似线性（约 0.011ms/单）：500 单 8ms → 2000 单 24ms → 6000 单 65ms。按此外推 3 秒
   上限约在 25 万单才兜底；500ms 上限约在 4–5 万单兜底——对记账本规模（几百到几千单）
   仍有几十倍余量，慢机器（CI/Windows 按 5 倍慢估）也安全。
3. **它现在能抓住什么**：历史上真出过的事故级劣化（R63 前「300 张单点一下列表等 2.7 秒」
   的逐单 9 查询那类）如果复发，在 561 单规模约 5 秒 > 3 秒，**能被抓住**——所以锁不是
   摆设，但只兜「灾难」不兜「缓慢劣化」。收紧到 500ms 后，10 倍级劣化（90ms→超标边缘、
   100 倍必红）开始有约束力。
4. 附带说明：listOrderRows 是全量取出算钱后 JS 内切片，耗时随**总单量**线性涨、与页大小
   无关——所以「500 单规模」这个轴选得对，SQL 快路径（M5 挂账）正是改这个量的。

## 四、口径自纠核对（git show HEAD:scripts/e2e-test.ts 的 R80 段，三处都在）

1. **total 与行数不同口径的处理——在**。`before80` 用 `listOrderRows({})` 读同口径基线
   （带注释「total 排除非 billing…全表 COUNT 会差出前面段的 5 张」），断言全部做前后
   同查询对比（rows 61→561、total 61→561、清理后回到 61/61）。**这个设计稳健**：不管
   口径差多少，前后都减得干净。但我实证了排除集与注释说法有出入（见第五节第 3 条）。
2. **清理断言同口径化——在**。清理后用 `afterCleanupRows`（listOrderRows）对 before80 的
   rows/total，不再拿全表 COUNT 对。顺带一句：旁边留了个算完没用的 `afterCleanup`
   （全表 COUNT）死变量，缩进也歪了一格——纯化妆品问题。
3. **测试单转「待确认」——在**（形态是「直插时就写 confirmed」）。500 张直插
   `payment_status='confirmed'`，与 API 建单后转待确认等价。但研发给的理由「草稿不在
   rows」**与事实不符**（见下节实证），结论歪打正着。

## 五、疑点 / 观察项

1. **「基线数值留档」名不副实（本轮最实在的缺口）**：`check()` 通过时只打 `✓ 名称`，
   detail（含 ms 数）**只在失败时才打印**（e2e-test.ts:56-64）。也就是说绿色通过时这组
   基线数字不落在任何地方——研发报告里也没写数值，而「留档供未来优化对比」恰恰是这轮
   的立轮之本。本报告第二节已把 9/9/8ms 抄录在案，但建议下轮顺手一行改掉：perf 类断言
   通过时也把 detail 打出来（或把数值写进 backend-plan 记账）。
2. **深翻页断言「能出」没验**：offset = 500×8 = 4000 > 总行数 561，切片出来是**空页**，
   断言只查了 `lastMs < 3000`，没查 rows 非空——「深翻页（第 8 页）也能出」这句名不副实。
   作为耗时探针它仍然有效（一样要全量算钱），但「能出」两个字目前是空的。要真验深翻页
   得把 offset 压到数据内（如 7×20=140），或把造数加到 4000+。
3. **两处口径注释与机制不符（实证）**：我逐个状态插库实测——**draft 计入 total（0→1）、
   expired 计入（1→2）、只有 void 不计入（2→2）**。即 `listWhere` 默认只排除「已作废」，
   注释里「total 排除非 billing（作废/失效）」只对了一半（失效/草稿都算），自纠③的理由
   「草稿不在 rows」也是错的（草稿明明计入）。好在断言本身做的是**同查询前后对比**，
   口径差在减法里自动抵消，结论不受影响——机制说错了，数学没错。
4. **3 秒上限建议收紧**：见第三节，建议 500ms（下轮顺手改一个数字的事，改前先看本报告
   第二节的实测基线）。
5. sweep 九路由与基线一致这句，我按提交范围核的（未触渲染层，renderer 产物与 R79 相同），
   没有单独跑 sweep——UI 不变由提交范围保证，另加 `/orders` 截图佐证（见第六节）。
