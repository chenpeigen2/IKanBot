## 二、逐项亲验记录

### ① 「搬迁上传」HTTP 五条——真上传真恢复，口径全对

（log 第 3656 行起，全部真 HTTP 请求）

1. 「上传是写操作，无 token 401」——鉴权同备份簇，口径对；
2. 「不是 zip 的字节被当场退回（人话）」——传 `definitely not a zip file` → 400，消息含「备份包」
   （core 里那句「这不是一份 IKanBot 备份包（zip），请从老桌面重新导出整库」——先查 zip 魔数字节
   0x50 0x4b 再落盘，坏字节进不了备份目录）；
3. 「整库包上传成功：落在服务器备份目录并带回摘要」——真拿服务器刚打的整库包字节原样传，
   回 200、路径是**新文件**（≠ 原包，uniqueBackupName 防撞名实锤）、hasDb=true、orderCount>0；
4. 「上传的包走既有恢复闸门成功」——恢复走的是**原有的** `/api/backup/restore`，两步分开，
   不是上传即恢复，「先看摘要再确认替换」的规矩没被绕开；
5. 「恢复响应带搬迁对账：表行数在、收款合计是数、单号唯一、抵扣台账合计是数」——report 四个
   口径字段逐个断言。

### ② 「老桌面带来的本机包」双模式两条——真演练，剧情是我最关心的那条

（`scripts/mode-test.ts:784` 起）测试把**服务器包的字节复制成本机临时文件**，伪装「老桌面导出的
整库包」，然后走真桌面 IPC：

1. 「inspect 时自动上传，摘要是服务器那份」——对**本机路径**调 `backup:inspect`，返回的 path 落在
   **服务器备份目录**（startsWith backups）且 hasDb=true——本机包真被搬上去了；
2. 「恢复成功（上传缓存命中不重传）且带搬迁对账」——同一本机路径再调 `backup:restore`，成功、
   带完整 report（orders>0、单号唯一）。

接线代码我也读了（`electron/ipc/index.ts:537` `resolveRemoteBackupPath`）：本机存在 → `remoteUploadBackup`
先传；本机不存在（服务器列表里的包）→ 原样转发不受影响；本机模式零改动（直接走本机 inspect/restore）。
远端 client 的缓存（`uploadedBackupCache`，同一本机路径会话内只传一次）在 `electron/remote/client.ts:299`。

### ③ 「搬迁对账」桌面节——增量指纹口径是我认的口径

（log 第 1075 行起）研发没用整库 SUM 当断言（会被全套测试垫底、绝对数不稳），而是「前后差一张」：
真建一客户、一单、一明细、一笔 72 元收款，前后各跑一次 migrationReport——

1. 「orders 行数 +1（表行数指纹）」；2. 「order_items 行数 +1」；3. 「payments 行数 +1 且收款合计
**恰好 +72**」；4. 「单号唯一在搬迁口径下成立（行数 = 去重单号数）」；5. 「抵扣台账合计是数（本轮没造
抵扣，不变）」；6. 「核心表一张不缺（12 张全在对账里）」——orders/order_items/customers/products/
quotations/quotation_items/sample_orders/sample_order_items/payments/order_events/packing_lists/
credit_applications 十二张，一张不少。**增量才是搬没搬对的判据，这个口径我认。**

实现（`core/migration.ts`）与断言一致：12 张表逐表 COUNT + 三指纹（SUM(payments.amount)、
orders 行数对 DISTINCT(order_no)、credit_applications 里 reversed_at IS NULL 的合计）；
预收派生余额逐客户抽查明说留第二版（要与 credits 域共用同一份派生算法才有意义）——挂账诚实。

## 三、新发现 / 疑点

1. **「九条」又是按属性分组数的**（R64 的「七条」同款）：R66 节实际 8 个 check（其中「payments 行数 +1
   且收款合计恰好 +72」一条断了两件事，按属性拆是 9）。增量账（+13/+2/+5）本身精确无虚报，
   我把 +13 的真实构成补进了第一节——这属口径习惯不算虚报，但建议以后报「X 条」时报 check 数。
2. **「上传缓存命中不重传」是代码实锤、无行为断言**：双模式那条断言名里带「缓存命中不重传」，
   但 check 体只验「恢复成功 + 带 report」——若缓存失效、第二次上传多落一份包，恢复照样成功、
   断言照样绿。缓存逻辑我在 `electron/remote/client.ts:299` 读实了（同一本机路径 get 命中直接返回
   服务器路径），且就算失效也只多一份重复包、不伤账。风险极低，记一笔：这半个口径目前靠代码
   正确性撑着，下轮顺手补一条「backups 目录里不出现同源双包」之类的断言更稳。
3. **上传路径的版本守卫没有专属断言**：与列表恢复共用同一个 inspect 函数（代码同路即同闸），
   且 restore 路径的 v999 人话守卫有现成三条断言锁着；但「传一个 v26 的包上来被拒」这个具体剧情
   没有直接断言。同一函数、风险极低，记一笔不下探。

3. **sweep 九路由**：本轮无界面变更（上传与对账都是数据层/协议层），研发未跑、我也未跑，
