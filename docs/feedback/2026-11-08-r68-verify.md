## 二、逐项亲验记录

### ① 余额算法同源——money 域同一份函数，没另写算法（这是本轮的命，逐行读了）

`git show HEAD:core/migration.ts`：

- `const balances = moneyCore(db).customerCreditBalance`——逐客户余额**逐个调 money 域的同一份函数**
  （与客户页「可用预收」同源），migration.ts 里没有任何自己写的派生算式；零余额行过滤。
- 候选客户确实是**并集**：`payments JOIN orders 的客户 ∪ credit_applications 的客户`（一条
  UNION SQL），注释里把第一版的坑写明白了（「没用掉的预收不落 credit_applications，只查台账
  会漏掉刚多收的客户——R68 第一版就栽在这」）。报告说的红（creditBalances 为空数组）与这个
  缺口形状吻合，红验证我认账。

HTTP 断言也是照这个最刁的形态造的：**无明细单**（合计 0）收进 1000 → 全额进预收 → 打包 → 恢复 →
对账里 `creditBalances` 必须有「R68 Prepaid Co / USD / 1000」——恰好是「只查台账会漏」的那类客户，
断言真刀真枪（真建单真收款真打包真恢复，`server/test/e2e.ts:1265` 起）。

## 三、新发现 / 疑点

1. **报告与 r68 README 都说「截图 2 张入库」，实际只入库 1 张**（`settings-restore-report.png`），
   「带客户预收余额行」的 `settings-restore-report-prepaid.png` 不在提交里（`git show ea11e6f --stat`
   只有 1 张 png；工作区也无未跟踪图）。报告把「截图 2 张入库」标了「已做并验过」——按「写了做了的
   必须真验过」的纪律这是虚报（大概率是 git add 漏了那张，README 都写好了）。行为本身无恙：
   数据层有 server e2e 锁、渲染形态我亲手复现为正常。**下轮必须补交那张图**（拍法 README 里就有）。
2. **补算标记写在恢复动作之前，恢复失败会留一个孤儿标记**：`backup:restore` 先写 pending 再调
   restoreBackup——恢复失败时标记已落盘，下次启动会对**没换过的库**补算一份对账写进
   `last_restore_report`，设置页会出现「最近一次恢复」的卡（其实是「最近一次恢复尝试」）。
   账面无害（数字是当前库的真实现算），但语义有点糊。建议：标记改在恢复成功后、进程退出前写
   （窗口虽窄但 restoring 状态可判），或补算时核对操作历史里最近一次 restore 是否成功。记下轮。
3. **seed 不清 `last_restore_report`**：我在干净复验时发现 seed 重灌后这个 settings 键会残留
   （我预置的摆拍行 seed 后还在）。R63 有先例（d851ffd 把 lastBackupAt 归零，理由就是基线要能
   复现）——同一类账：真实用户恢复过再 seed，/settings 的截图与 sweep 基线会多一张对账卡。
   建议 seed 把这个键一并归零。记下轮。
4. 「吞错场景红验证不可达」的诚实标注我核过：同机双模式里本机副本永远存在，纯远端场景测试
   够不着——判据替换让吞错路径不复存在 + 透传行为有断言，覆盖成立，这条不算欠账。
