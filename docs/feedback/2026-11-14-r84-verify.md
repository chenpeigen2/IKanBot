## 五、口径同源复核（dataHealthCheck vs inspectRestoredDb→assertDbProbeUsable）

逐闸对表（core/settings.ts:380-412 vs core/backup.ts:358-384）：

| 闸 | 备份/恢复探针 | 数据自检 | 同口径？ |
|---|---|---|---|
| 自检 | `String(check?.quick_check ?? '') !== 'ok'` → 拦 | 同款取法 + `quickCheck !== 'ok'` → push 人话 | **同**（同字面量、同 `?? ''` 空值处理、同方向） |
| 版本 | `v > LATEST_DB_VERSION` → 拦 | `ver > LATEST_DB_VERSION` → push 人话 | **同**（同一个常量，两边都 import 自 electron/db/schema，单一来源） |
| 核心表 | COUNT orders+payments，`!orders \|\| !payments` → 拦 | 12 表逐一 COUNT（含这两张，超集），抛错 catch → push 人话、记 -1 | **同语义超集**，方向一致（自检更严不更松） |

`ok = problems.length === 0` 之后探针语义仍一致：探针拦的三种情况（quick_check ✗ / 版本超前 /
orders·payments COUNT 抛错）在自检里 problems **必非空** ✓。一个理论注脚（不挡放行）：探针的
`!orders || !payments` 还覆盖「COUNT 返回 null」的路径，自检里 `Number(r?.n ?? 0)` 会把 null
当 0、不进 problems——但 COUNT(*) 恒返回一行，null 得适配层坏掉才出现，实际到不了；且自检在
抛错路径上 12 表任一都接，比探针只查两张更严。R67「别让两条路各说各话」的教训继续守住。
